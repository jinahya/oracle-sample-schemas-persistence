Exercises for the `HR` sample schema. Each problem is a request that someone working for the company — an HR
manager, payroll, a department head, facilities, an auditor — might bring to you; answer it with a query. Every
solution is given twice: as Oracle SQL against the installed schema (see the link:../../../README.md[README] for its tables and
columns), and as JPQL — the Jakarta Persistence 3.2 query language — against this module's entities.

The problems are grouped by the table or view they read, in the order of the README, and within each by difficulty:
Basic, Intermediate and Advanced. A problem that joins, or subqueries, more than one table is under Whole schema, the
last section.

A few things to keep in mind while reading the JPQL:

* The entity names are the class names — `Region`, `Country`, `Location`, `Department`, `Employee`, `Job` — except
  for `+JOB_HISTORY+`, mapped by `JobHistory`. It maps its composite key with an `+@IdClass+`, so the key attributes
  are on the entity itself (`h.employeeId`, `h.startDate`).
* A foreign key is mapped twice: as an association on the entity, and as a read-only attribute on its mapped
  superclass, `Employee.departmentId` or `Department.locationId`. The answers below navigate the association, as
  `e.department.departmentId` or `d.location.locationId`, or compare it with an entity parameter, as
  `+e.department = :department+`; the read-only attribute gives the same key without the path.
* `+EMP_DETAILS_VIEW+` is mapped by `EmpDetailsView`, which both persistence units list; its problems are solved in
  SQL only.
* Parameters are named (`:departmentId`). Bind them with `setParameter`; Oracle tools such as SQL{asterisk}Plus and SQLcl
  prompt for, or take, the same names as bind variables.

[[HR_COUNTRIES_A_01]]
==== HR_COUNTRIES_A_01: Regions above the average size

Head office wants the regions that cover more countries than a region does on average.

[source,sql]
----
SELECT REGION_ID, COUNT(*) AS COUNTRIES
FROM COUNTRIES
GROUP BY REGION_ID
HAVING COUNT(*) > (SELECT COUNT(*) / COUNT(DISTINCT REGION_ID) FROM COUNTRIES)
ORDER BY COUNTRIES DESC
----

[source,jpaql]
----
SELECT c.region.regionId, COUNT(c) AS countries
FROM Country c
GROUP BY c.region.regionId
HAVING COUNT(c) > (SELECT COUNT(x) * 1.0 / COUNT(DISTINCT x.region) FROM Country x)
ORDER BY countries DESC
----

The average is the number of countries over the number of regions that have any. `COUNT` returns a `Long`, and in
JPQL — as in Java — dividing one integer by another truncates, under both providers; `+* 1.0+` keeps the fraction.
Oracle's `+/+` never truncates.

==== HR_EMPLOYEES_A_04: Out-earning a whole department

Before a salary benchmark, HR asks two things about a reference department (given its id): who earns more than
_everyone_ in it, and who earns more than _at least one_ person in it.

[source,sql]
----
SELECT EMPLOYEE_ID, LAST_NAME, SALARY
FROM EMPLOYEES
WHERE SALARY > ALL (SELECT SALARY FROM EMPLOYEES WHERE DEPARTMENT_ID = :departmentId)
ORDER BY SALARY DESC
----

[source,jpaql]
----
SELECT e.employeeId, e.lastName, e.salary
FROM Employee e
WHERE e.salary > ALL (SELECT x.salary FROM Employee x WHERE x.department.departmentId = :departmentId)
ORDER BY e.salary DESC
----

[source,sql]
----
SELECT EMPLOYEE_ID, LAST_NAME, SALARY
FROM EMPLOYEES
WHERE SALARY > ANY (SELECT SALARY FROM EMPLOYEES WHERE DEPARTMENT_ID = :departmentId)
ORDER BY SALARY DESC
----

[source,jpaql]
----
SELECT e.employeeId, e.lastName, e.salary
FROM Employee e
WHERE e.salary > ANY (SELECT x.salary FROM Employee x WHERE x.department.departmentId = :departmentId)
ORDER BY e.salary DESC
----

`SALARY` is nullable. A single null in the subquery makes `+> ALL+` unknown for every row — nobody qualifies — while
`+> ANY+` just ignores it. No salary is null in the installed data. Also note that `+> ALL+` of an empty subquery (a
department with no staff) is true for everyone.

____
https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2#a5587[4.10. ORDER BY Clause]

The keyword `NULLS` specifies the ordering of null values, either `FIRST` or `LAST`.

* `FIRST` means that results are sorted so that all null values occur before all non-null values.

* `LAST` means that results are sorted so that all null values occur after all non-null values.

If `NULLS` is not specified, the database determines whether null values occur first or last.
____

[source,sql]
----
SELECT *
FROM JOBS
ORDER BY MIN_SALARY ASC NULLS FIRST, JOB_ID ASC
----

[source,jpaql]
----
SELECT j
FROM Job j
ORDER BY j.minSalary ASC NULLS FIRST, j.jobId ASC
----

[source,sql]
----
SELECT *
FROM JOBS
ORDER BY MAX_SALARY DESC NULLS LAST, JOB_ID ASC
----

[source,jpaql]
----
SELECT j
FROM Job j
ORDER BY j.maxSalary DESC NULLS LAST, j.jobId ASC
----

Every job in the installed data has both values, so the `NULLS` clauses decide nothing yet; they make the order
explicit for the day a job is added without a band. Oracle sorts nulls last ascending and first descending by default
— the opposite of what was asked here.

==== HR_SCHEMA_I_07: Departments with nobody in them

Facilities wants to reclaim space from departments that have no employees, and to know whether each still has a manager
on record.

[source,sql]
----
SELECT d.DEPARTMENT_ID, d.DEPARTMENT_NAME, d.MANAGER_ID
FROM DEPARTMENTS d
WHERE NOT EXISTS (SELECT 1 FROM EMPLOYEES e WHERE e.DEPARTMENT_ID = d.DEPARTMENT_ID)
ORDER BY d.DEPARTMENT_ID ASC
----

[source,jpaql]
----
SELECT d.departmentId, d.departmentName, m.employeeId
FROM Department d
         LEFT JOIN d.manager m
WHERE d.employees IS EMPTY
ORDER BY d.departmentId ASC
----

Sixteen of the twenty-seven departments are empty in the installed data, and none of those has a manager.

==== HR_SCHEMA_A_03: Back in an earlier job

HR wants the employees whose current job is one they held before — boomerangs within the company.

[source,sql]
----
SELECT EMPLOYEE_ID, JOB_ID
FROM JOB_HISTORY
INTERSECT
SELECT EMPLOYEE_ID, JOB_ID
FROM EMPLOYEES
ORDER BY 1
----

[source,jpaql]
----
SELECT h.employeeId, h.job.jobId
FROM JobHistory h
INTERSECT
SELECT e.employeeId, e.job.jobId
FROM Employee e
----

[source,jpaql]
----
SELECT DISTINCT e.employeeId, e.job.jobId
FROM Employee e
         JOIN e.jobHistories h
WHERE h.job = e.job
----

The `INTERSECT` form needs Jakarta Persistence 3.2; the join works with any version.

==== HR_SCHEMA_A_05: Department roster in one round trip

The intranet's site page shows, for one location, each department and its staff, the empty departments included, the staff by last name, first name and `EMPLOYEE_ID`.
Loading the departments and then each one's employees is the N+1 problem; the page needs a single query, with each column named once.

[source,sql]
----
SELECT d.DEPARTMENT_ID, d.DEPARTMENT_NAME, e.EMPLOYEE_ID, e.FIRST_NAME, e.LAST_NAME, e.JOB_ID
FROM DEPARTMENTS d
         LEFT JOIN EMPLOYEES e ON e.DEPARTMENT_ID = d.DEPARTMENT_ID
WHERE d.LOCATION_ID = :locationId
ORDER BY d.DEPARTMENT_ID ASC, e.LAST_NAME ASC, e.FIRST_NAME ASC NULLS FIRST, e.EMPLOYEE_ID ASC
----

[source,jpaql]
----
SELECT DISTINCT d
FROM Department d
         LEFT JOIN FETCH d.employees
WHERE d.location.locationId = :locationId
ORDER BY d.departmentId ASC
----

[source,jpaql]
----
SELECT e
FROM Employee e
         JOIN FETCH e.job
         LEFT JOIN FETCH e.department
WHERE e.department.departmentId = :departmentId
ORDER BY e.lastName ASC
----

Every association here is `LAZY`, so without `FETCH` each `getEmployees()` or `getJob()` call outside the query would
issue its own `SELECT`. `DISTINCT` removes the repeated `Department` the collection join produces. Do not combine a
collection fetch join with `setMaxResults`: the limit applies to joined rows, so providers either paginate in memory
or cut a department's staff list short.
