= Exercises
:toc: left
:toclevels: 3
:sectanchors:
:source-highlighter: rouge

Exercises for the `HR` sample schema. Each problem is a request that someone working for the company — an HR
manager, payroll, a department head, facilities, an auditor — might bring to you; answer it with a query. Every
solution is given twice: as Oracle SQL against the installed schema (see the link:../../../README.md[README] for its tables and
columns), and as JPQL — the Jakarta Persistence 3.2 query language — against this module's entities.

The problems are grouped by the table or view they read, in the order of the README, and within each by difficulty:
Basic, Intermediate and Advanced. A problem that joins, or subqueries, more than one table is under Whole schema, the
last section.

A few things to keep in mind while reading the JPQL:

* The entity names are the class names — `Region`, `Country`, `Location`, `Department`, `Employee`, `Job` — except
  for `+JOB_HISTORY+`, mapped by `JobHistory`. It maps its composite key with an `+@IdClass+`, so the key attributes
  are on the entity itself (`h.employeeId`, `h.startDate`).
* A foreign key is mapped twice: as an association on the entity, and as a read-only attribute on its mapped
  superclass, `Employee.departmentId` or `Department.locationId`. The answers below navigate the association, as
  `e.department.departmentId` or `d.location.locationId`, or compare it with an entity parameter, as
  `+e.department = :department+`; the read-only attribute gives the same key without the path.
* `+EMP_DETAILS_VIEW+` is mapped by `EmpDetailsView`, which both persistence units list; its problems are solved in
  SQL only.
* Parameters are named (`:departmentId`). Bind them with `setParameter`; Oracle tools such as SQL{asterisk}Plus and SQLcl
  prompt for, or take, the same names as bind variables.

== COUNTRIES

=== Basic

[[HR_COUNTRIES_B_01]]
==== HR_COUNTRIES_B_01: Country by code

The shipping form has a two-letter country code, such as `US`, and needs the country's name.

[source,sql]
----
SELECT COUNTRY_NAME
FROM COUNTRIES
WHERE COUNTRY_ID = :countryId
----

[source,jpaql]
----
SELECT c.countryName
FROM Country c
WHERE c.countryId = :countryId
----

[[HR_COUNTRIES_B_02]]
==== HR_COUNTRIES_B_02: Countries of a region

A regional director wants the countries of their region (given the region id), alphabetically.

[source,sql]
----
SELECT COUNTRY_ID, COUNTRY_NAME
FROM COUNTRIES
WHERE REGION_ID = :regionId
ORDER BY COUNTRY_NAME ASC
----

[source,jpaql]
----
SELECT c.countryId, c.countryName
FROM Country c
WHERE c.region.regionId = :regionId
ORDER BY c.countryName ASC
----

`Region.regionId` is a `Long` (the column is an unconstrained `NUMBER`), so bind a `Long`, e.g. `10L`.

[[HR_COUNTRIES_B_03]]
==== HR_COUNTRIES_B_03: Country names too long for a badge

The badge printer's country field holds 20 characters. Which country names will not fit?

[source,sql]
----
SELECT COUNTRY_ID, COUNTRY_NAME, LENGTH(COUNTRY_NAME) AS NAME_LENGTH
FROM COUNTRIES
WHERE LENGTH(COUNTRY_NAME) > :maxLength
ORDER BY NAME_LENGTH DESC
----

[source,jpaql]
----
SELECT c.countryId, c.countryName, LENGTH(c.countryName) AS nameLength
FROM Country c
WHERE LENGTH(c.countryName) > :maxLength
ORDER BY nameLength DESC
----

=== Intermediate

[[HR_COUNTRIES_I_01]]
==== HR_COUNTRIES_I_01: Countries per region

The regional directors compare territories: how many countries each region covers, most first.

[source,sql]
----
SELECT REGION_ID, COUNT(*) AS COUNTRIES
FROM COUNTRIES
GROUP BY REGION_ID
ORDER BY COUNTRIES DESC, REGION_ID ASC
----

[source,jpaql]
----
SELECT c.region.regionId, COUNT(c) AS countries
FROM Country c
GROUP BY c.region.regionId
ORDER BY countries DESC, c.region.regionId ASC
----

The region's name is in `REGIONS`; this table has only its id. A country without a region would form a group of its
own, with a null id — none does in the installed data.

=== Advanced

[[HR_COUNTRIES_A_01]]
==== HR_COUNTRIES_A_01: Regions above the average size

Head office wants the regions that cover more countries than a region does on average.

[source,sql]
----
SELECT REGION_ID, COUNT(*) AS COUNTRIES
FROM COUNTRIES
GROUP BY REGION_ID
HAVING COUNT(*) > (SELECT COUNT(*) / COUNT(DISTINCT REGION_ID) FROM COUNTRIES)
ORDER BY COUNTRIES DESC
----

[source,jpaql]
----
SELECT c.region.regionId, COUNT(c) AS countries
FROM Country c
GROUP BY c.region.regionId
HAVING COUNT(c) > (SELECT COUNT(x) * 1.0 / COUNT(DISTINCT x.region) FROM Country x)
ORDER BY countries DESC
----

The average is the number of countries over the number of regions that have any. `COUNT` returns a `Long`, and in
JPQL — as in Java — dividing one integer by another truncates, under both providers; `+* 1.0+` keeps the fraction.
Oracle's `+/+` never truncates.

[[HR_DEPARTMENTS_I_02]]
==== HR_DEPARTMENTS_I_02: Departments at a glance

HR's quarterly dashboard shows three numbers: how many departments there are, how many of them have a manager, and on
how many sites they sit.

[source,sql]
----
SELECT COUNT(*) AS DEPARTMENTS, COUNT(MANAGER_ID) AS MANAGED, COUNT(DISTINCT LOCATION_ID) AS SITES
FROM DEPARTMENTS
----

[source,jpaql]
----
SELECT COUNT(d), COUNT(d.manager), COUNT(DISTINCT d.location)
FROM Department d
----

[source,jpaql]
----
SELECT COUNT(d), COUNT(m), COUNT(DISTINCT l)
FROM Department d
         LEFT JOIN d.manager m
         LEFT JOIN d.location l
----

`COUNT` of a column or of an association counts the rows where it is not null, which is what makes the second number
differ from the first: 27 departments, 11 managed, on 7 sites. Hibernate ORM returns that for both JPQL forms.
EclipseLink 5.0.1, however, turns `d.manager` in the first form into an inner join to `EMPLOYEES`, which drops the
unmanaged departments from `COUNT(d)` as well, and returns 11, 11, 7. The explicit `LEFT JOIN` form gives 27, 11, 7
under both.

=== Advanced

[[HR_DEPARTMENTS_A_01]]
==== HR_DEPARTMENTS_A_01: Next free department number

Department numbers go up in tens. Before creating a department, HR wants the lowest number that follows an existing
department and is not taken yet.

[source,sql]
----
SELECT MIN(d.DEPARTMENT_ID + 10) AS NEXT_FREE
FROM DEPARTMENTS d
WHERE NOT EXISTS (SELECT 1 FROM DEPARTMENTS x WHERE x.DEPARTMENT_ID = d.DEPARTMENT_ID + 10)
----

[source,jpaql]
----
SELECT MIN(d.departmentId + 10)
FROM Department d
WHERE NOT EXISTS (SELECT x FROM Department x WHERE x.departmentId = d.departmentId + 10)
----

The installed numbering has no gaps, so the answer is 280; once a department is deleted, its number is the answer
instead, which `+MAX(DEPARTMENT_ID) + 10+` would skip. Two sessions asking at once get the same number, so this answers
a planning question; it does not hand out keys. Strictly, the JPQL grammar takes only a path inside `MIN`, not an
expression; both providers accept it.

[[HR_EMPLOYEES_B_06]]
==== HR_EMPLOYEES_B_06: Hired in a period

HR is preparing the probation review for everyone hired in a given period, the from and to dates both included, the earliest hires first; people hired on one day are ordered by `EMPLOYEE_ID`.
A `DATE` has a time of day, so the period runs from `TRUNC(:fromDate)` up to, not including, the day after `:toDate`.

[source,sql]
----
SELECT *
FROM EMPLOYEES
WHERE HIRE_DATE >= TRUNC(:fromDate)
  AND HIRE_DATE < TRUNC(:toDate) + 1
ORDER BY HIRE_DATE ASC, EMPLOYEE_ID ASC
----

[source,jpaql]
----
SELECT e
FROM Employee e
WHERE e.hireDate BETWEEN :fromDate AND :toDate
ORDER BY e.hireDate ASC
----

// JPQL NOT YET UPDATED: the SQL above changed.

`hireDate` is a `java.time.LocalDate`, so bind `LocalDate` values. In SQL, `BETWEEN` is inclusive at both ends only
because every `+HIRE_DATE+` in the data is at midnight; a `DATE` with a time-of-day after `:toDate` would be missed.

[[HR_EMPLOYEES_B_07]]
==== HR_EMPLOYEES_B_07: Name search at reception

Reception has part of a surname over the phone and needs the matching employees, whatever the case typed.

[source,sql]
----
SELECT EMPLOYEE_ID, FIRST_NAME, LAST_NAME, PHONE_NUMBER
FROM EMPLOYEES
WHERE UPPER(LAST_NAME) LIKE UPPER(:pattern)
ORDER BY LAST_NAME ASC, FIRST_NAME ASC
----

[source,jpaql]
----
SELECT e.employeeId, e.firstName, e.lastName, e.phoneNumber
FROM Employee e
WHERE UPPER(e.lastName) LIKE :pattern
ORDER BY e.lastName ASC, e.firstName ASC
----

The caller passes the wildcard, e.g. `+K%+` for "starts with K". In JPQL the pattern of `LIKE` must be a string literal
or an input parameter, not an expression, so the caller also upper-cases it (`+input.toUpperCase() + "%"+`) rather than
the query wrapping it in `UPPER(...)` or appending the `+%+` with `+||+`.

[[HR_EMPLOYEES_I_02]]
==== HR_EMPLOYEES_I_02: Total monthly pay including commission

Payroll needs each employee's expected monthly pay: salary plus commission, where commission is a rate on salary and is
absent for most staff. Label each employee as commissioned or salaried.

[source,sql]
----
SELECT EMPLOYEE_ID, LAST_NAME, SALARY, COMMISSION_PCT,
       SALARY * (1 + COALESCE(COMMISSION_PCT, 0)) AS TOTAL_PAY,
       CASE WHEN COMMISSION_PCT IS NULL THEN 'Salaried' ELSE 'Commissioned' END AS PAY_TYPE
FROM EMPLOYEES
ORDER BY TOTAL_PAY DESC
----

[source,jpaql]
----
SELECT e.employeeId, e.lastName, e.salary, e.commissionPct,
       e.salary * (1 + COALESCE(e.commissionPct, 0)) AS totalPay,
       CASE WHEN e.commissionPct IS NULL THEN 'Salaried' ELSE 'Commissioned' END
FROM Employee e
ORDER BY totalPay DESC
----

Without `COALESCE`, `+SALARY * (1 + NULL)+` is null and every salaried employee would have no pay at all.

[[HR_EMPLOYEES_I_03]]
==== HR_EMPLOYEES_I_03: Headcount per pay grade

HR reports headcount in three pay grades: under 5,000, 5,000 up to 10,000, and 10,000 or more, with the employees whose salary is not recorded in a fourth, `Not recorded`.
Show the grades from the lowest to the highest, `Not recorded` last.

[source,sql]
----
SELECT CASE
           WHEN SALARY IS NULL THEN 'Not recorded'
           WHEN SALARY < 5000 THEN 'Low'
           WHEN SALARY < 10000 THEN 'Medium'
           ELSE 'High'
           END  AS GRADE,
       COUNT(*) AS HEADCOUNT
FROM EMPLOYEES
GROUP BY CASE
             WHEN SALARY IS NULL THEN 'Not recorded'
             WHEN SALARY < 5000 THEN 'Low'
             WHEN SALARY < 10000 THEN 'Medium'
             ELSE 'High'
             END
ORDER BY MIN(SALARY) ASC NULLS LAST
----

// NOT YET RUN

[source,jpaql]
----
SELECT SUM(CASE WHEN e.salary < 5000 THEN 1 ELSE 0 END),
       SUM(CASE WHEN e.salary >= 5000 AND e.salary < 10000 THEN 1 ELSE 0 END),
       SUM(CASE WHEN e.salary >= 10000 THEN 1 ELSE 0 END)
FROM Employee e
----

// JPQL NOT YET UPDATED: the SQL above changed.

JPQL's `GROUP BY` takes only paths and identification variables, not a `CASE` expression, so the portable answer
turns the grades into columns of a single row instead of rows.

[[HR_EMPLOYEES_I_05]]
==== HR_EMPLOYEES_I_05: Span of control

The COO wants every manager with the number of people reporting directly to them, most first.

[source,sql]
----
SELECT m.EMPLOYEE_ID, m.FIRST_NAME, m.LAST_NAME, COUNT(*) AS DIRECT_REPORTS
FROM EMPLOYEES m
         JOIN EMPLOYEES e ON e.MANAGER_ID = m.EMPLOYEE_ID
GROUP BY m.EMPLOYEE_ID, m.FIRST_NAME, m.LAST_NAME
ORDER BY DIRECT_REPORTS DESC, m.EMPLOYEE_ID ASC
----

[source,jpaql]
----
SELECT m.employeeId, m.firstName, m.lastName, COUNT(s) AS directReports
FROM Employee m
         JOIN m.subordinates s
GROUP BY m.employeeId, m.firstName, m.lastName
ORDER BY directReports DESC, m.employeeId ASC
----

[source,jpaql]
----
SELECT m, SIZE(m.subordinates) AS directReports
FROM Employee m
WHERE m.subordinates IS NOT EMPTY
ORDER BY directReports DESC, m.employeeId ASC
----

A result variable cannot be filtered on in `WHERE` — `+WHERE directReports > 0+` is not JPQL. Filter on the collection
itself (`IS NOT EMPTY`, or `+SIZE(m.subordinates) > 0+`), or let the inner join drop managers with nobody.

[[HR_EMPLOYEES_I_06]]
==== HR_EMPLOYEES_I_06: Skip-level meetings

A vice president holds skip-level meetings: they meet the people who report to their direct reports. Given the vice
president, list those employees with the manager in between, by name.

[source,sql]
----
SELECT e.EMPLOYEE_ID, e.FIRST_NAME, e.LAST_NAME, m.LAST_NAME AS MANAGER
FROM EMPLOYEES e
         JOIN EMPLOYEES m ON m.EMPLOYEE_ID = e.MANAGER_ID
WHERE m.MANAGER_ID = :managerId
ORDER BY e.LAST_NAME ASC, e.FIRST_NAME ASC
----

[source,jpaql]
----
SELECT e
FROM Employee e
WHERE e.manager.manager = :manager
ORDER BY e.lastName ASC, e.firstName ASC
----

In the JPQL, the path `e.manager.manager` is the self-join written as navigation: each step is an inner join, so an
employee without a manager, or whose manager has none, cannot match. `e.getManager()` then gives the manager in between.
For Neena Yang (`101`) the answer is the five accountants under Nancy Gruenberg and William Gietz under Shelley Higgins.

=== Advanced

[[HR_EMPLOYEES_A_01]]
==== HR_EMPLOYEES_A_01: Top earner of each department

Each department head is told who their best-paid employee is; ties are all reported, ordered by `EMPLOYEE_ID`.
An employee with no department, or no salary recorded, is left out, as the correlated solution leaves them out; HR_EMPLOYEES_B_09 lists the salaries not recorded.

[source,sql]
----
SELECT DEPARTMENT_ID, EMPLOYEE_ID, LAST_NAME, SALARY
FROM (SELECT e.*, RANK() OVER (PARTITION BY DEPARTMENT_ID ORDER BY SALARY DESC) AS RNK
      FROM EMPLOYEES e
      WHERE DEPARTMENT_ID IS NOT NULL
        AND SALARY IS NOT NULL)
WHERE RNK = 1
ORDER BY DEPARTMENT_ID ASC, EMPLOYEE_ID ASC
----

// NOT YET RUN

[source,sql]
----
SELECT DEPARTMENT_ID, EMPLOYEE_ID, LAST_NAME, SALARY
FROM (SELECT e.*, RANK() OVER (PARTITION BY DEPARTMENT_ID ORDER BY SALARY DESC) AS RNK
      FROM EMPLOYEES e)
WHERE RNK = 1
ORDER BY DEPARTMENT_ID ASC
----

[source,jpaql]
----
SELECT e.department.departmentId, e.employeeId, e.lastName, e.salary
FROM Employee e
WHERE e.salary = (SELECT MAX(x.salary) FROM Employee x WHERE x.department = e.department)
ORDER BY e.department.departmentId ASC
----

// JPQL NOT YET UPDATED: the SQL above changed.

The correlated subquery skips the employee without a department (`+x.department = NULL+` is never true); the analytic
form keeps them as a partition of their own. JPQL has no window functions (`RANK() OVER (...)`), so the correlated
subquery is the portable form.

[[HR_EMPLOYEES_A_02]]
==== HR_EMPLOYEES_A_02: Three best-paid per department

Ahead of the bonus round, each department head wants the three highest salaries of the department and everyone who earns one of them, ties included.
Salaries not recorded are left out, so they never take a rank; the people of one rank are ordered by `EMPLOYEE_ID`.

[source,sql]
----
SELECT DEPARTMENT_ID, EMPLOYEE_ID, LAST_NAME, SALARY, RNK
FROM (SELECT e.*, DENSE_RANK() OVER (PARTITION BY DEPARTMENT_ID ORDER BY SALARY DESC) AS RNK
      FROM EMPLOYEES e
      WHERE DEPARTMENT_ID IS NOT NULL
        AND SALARY IS NOT NULL)
WHERE RNK <= 3
ORDER BY DEPARTMENT_ID ASC, RNK ASC, EMPLOYEE_ID ASC
----

// NOT YET RUN

[source,jpaql]
----
SELECT e.department.departmentId, e.employeeId, e.lastName, e.salary
FROM Employee e
WHERE e.department IS NOT NULL
  AND (SELECT COUNT(DISTINCT x.salary)
       FROM Employee x
       WHERE x.department = e.department
         AND x.salary > e.salary) < 3
ORDER BY e.department.departmentId ASC, e.salary DESC
----

// JPQL NOT YET UPDATED: the SQL above changed.

The JPQL counts how many distinct salaries in the same department beat this one; fewer than three means it is among
the top three — the same as `+DENSE_RANK() <= 3+`. The `IS NOT NULL` test matters: for the employee without a
department the subquery counts nobody, and zero is less than three.

[[HR_EMPLOYEES_A_03]]
==== HR_EMPLOYEES_A_03: Everyone under a manager

For a reorganisation, HR needs everyone who reports to a given manager, directly or indirectly, with their depth below
that manager.

[source,sql]
----
SELECT LEVEL - 1 AS DEPTH, EMPLOYEE_ID, LAST_NAME, MANAGER_ID,
       SYS_CONNECT_BY_PATH(LAST_NAME, '/') AS CHAIN
FROM EMPLOYEES
WHERE LEVEL > 1
START WITH EMPLOYEE_ID = :managerId
CONNECT BY PRIOR EMPLOYEE_ID = MANAGER_ID
ORDER SIBLINGS BY LAST_NAME
----

[source,sql]
----
WITH CHAIN (EMPLOYEE_ID, LAST_NAME, MANAGER_ID, DEPTH) AS (
    SELECT EMPLOYEE_ID, LAST_NAME, MANAGER_ID, 0
    FROM EMPLOYEES
    WHERE EMPLOYEE_ID = :managerId
    UNION ALL
    SELECT e.EMPLOYEE_ID, e.LAST_NAME, e.MANAGER_ID, c.DEPTH + 1
    FROM EMPLOYEES e
             JOIN CHAIN c ON e.MANAGER_ID = c.EMPLOYEE_ID)
SELECT DEPTH, EMPLOYEE_ID, LAST_NAME, MANAGER_ID
FROM CHAIN
WHERE DEPTH > 0
ORDER BY DEPTH ASC, LAST_NAME ASC
----

[source,jpaql]
----
SELECT e
FROM Employee e
         JOIN e.manager m1
         LEFT JOIN m1.manager m2
         LEFT JOIN m2.manager m3
WHERE m1.employeeId = :managerId
   OR m2.employeeId = :managerId
   OR m3.employeeId = :managerId
ORDER BY e.lastName ASC
----

JPQL has no recursive query — neither `CONNECT BY` nor a recursive `WITH`. The JPQL above unrolls a fixed number of
levels (three, enough for any manager's subtree in the installed data, whose chain from the president is four deep).
For an unbounded depth, query level by level from Java — `SELECT e FROM Employee e WHERE e.manager IN :managers`,
feeding each level's result back in as `:managers` until it comes back empty — or walk `subordinates` in memory.

[[HR_EMPLOYEES_A_04]]
==== HR_EMPLOYEES_A_04: Out-earning a whole department

Before a salary benchmark, HR asks two things about a reference department (given its id): who earns more than
_everyone_ in it, and who earns more than _at least one_ person in it.

[source,sql]
----
SELECT EMPLOYEE_ID, LAST_NAME, SALARY
FROM EMPLOYEES
WHERE SALARY > ALL (SELECT SALARY FROM EMPLOYEES WHERE DEPARTMENT_ID = :departmentId)
ORDER BY SALARY DESC
----

[source,jpaql]
----
SELECT e.employeeId, e.lastName, e.salary
FROM Employee e
WHERE e.salary > ALL (SELECT x.salary FROM Employee x WHERE x.department.departmentId = :departmentId)
ORDER BY e.salary DESC
----

[source,sql]
----
SELECT EMPLOYEE_ID, LAST_NAME, SALARY
FROM EMPLOYEES
WHERE SALARY > ANY (SELECT SALARY FROM EMPLOYEES WHERE DEPARTMENT_ID = :departmentId)
ORDER BY SALARY DESC
----

[source,jpaql]
----
SELECT e.employeeId, e.lastName, e.salary
FROM Employee e
WHERE e.salary > ANY (SELECT x.salary FROM Employee x WHERE x.department.departmentId = :departmentId)
ORDER BY e.salary DESC
----

`SALARY` is nullable. A single null in the subquery makes `+> ALL+` unknown for every row — nobody qualifies — while
`+> ANY+` just ignores it. No salary is null in the installed data. Also note that `+> ALL+` of an empty subquery (a
department with no staff) is true for everyone.

[[HR_EMPLOYEES_A_05]]
==== HR_EMPLOYEES_A_05: Work anniversaries

HR sends a card on every work anniversary. Given a month (1–12), list who joined in that month and how many years they
complete this year.

[source,sql]
----
SELECT EMPLOYEE_ID, FIRST_NAME, LAST_NAME, HIRE_DATE,
       EXTRACT(YEAR FROM SYSDATE) - EXTRACT(YEAR FROM HIRE_DATE) AS YEARS
FROM EMPLOYEES
WHERE EXTRACT(MONTH FROM HIRE_DATE) = :month
ORDER BY EXTRACT(DAY FROM HIRE_DATE) ASC, LAST_NAME ASC
----

[source,jpaql]
----
SELECT e.employeeId, e.firstName, e.lastName, e.hireDate,
       EXTRACT(YEAR FROM LOCAL DATE) - EXTRACT(YEAR FROM e.hireDate)
FROM Employee e
WHERE EXTRACT(MONTH FROM e.hireDate) = :month
ORDER BY EXTRACT(DAY FROM e.hireDate) ASC, e.lastName ASC
----

[source,jpaql]
----
SELECT e.employeeId, e.firstName, e.lastName, e.hireDate,
       EXTRACT(YEAR FROM CURRENT_DATE) - EXTRACT(YEAR FROM e.hireDate)
FROM Employee e
WHERE EXTRACT(MONTH FROM e.hireDate) = :month
ORDER BY EXTRACT(DAY FROM e.hireDate) ASC, e.lastName ASC
----

`EXTRACT` and `LOCAL DATE` (a `java.time.LocalDate` evaluated on the database server) are new in Jakarta
Persistence 3.2; `:month` is an `Integer`. EclipseLink 5.0.1 fails to compile `LOCAL DATE` (an internal
`NullPointerException` in its parser), so the second form falls back to `+CURRENT_DATE+`, which both providers accept.
Subtracting calendar years counts the year about to be completed, which is what the card says.

[[HR_EMPLOYEES_A_06]]
==== HR_EMPLOYEES_A_06: Badges and e-mail migration

IT is moving everyone to full e-mail addresses and reprinting badges. For each employee they need a proposed address
(`+first.last@example.com+`, lower case), the badge line (`+EMP-+` and the id, then the last name and first initial), the
phone number with dashes instead of dots, and its last four digits for the desk extension.

[source,sql]
----
SELECT EMPLOYEE_ID,
       LOWER(COALESCE(FIRST_NAME, '') || '.' || LAST_NAME) || '@example.com' AS PROPOSED_EMAIL,
       'EMP-' || TO_CHAR(EMPLOYEE_ID) || ' ' || LAST_NAME || ', ' || SUBSTR(FIRST_NAME, 1, 1) || '.' AS BADGE,
       REPLACE(PHONE_NUMBER, '.', '-') AS PHONE,
       SUBSTR(PHONE_NUMBER, -4) AS LAST_FOUR
FROM EMPLOYEES
ORDER BY EMPLOYEE_ID ASC
----

[source,jpaql]
----
SELECT e.employeeId,
       LOWER(COALESCE(e.firstName, '') || '.' || e.lastName) || '@example.com',
       'EMP-' || CAST(e.employeeId AS STRING) || ' ' || e.lastName || ', ' || LEFT(e.firstName, 1) || '.',
       REPLACE(e.phoneNumber, '.', '-'),
       RIGHT(e.phoneNumber, 4)
FROM Employee e
ORDER BY e.employeeId ASC
----

`+||+`, `CAST(... AS STRING)`, `LEFT`, `RIGHT` and `REPLACE` are all new in Jakarta Persistence 3.2 (earlier versions
have `CONCAT` and `SUBSTRING`). In Oracle, `+||+` treats a null as an empty string, so the SQL badge still comes out for
a missing first name; standard SQL — and so JPQL on other databases — yields null for the whole expression, which is
why the e-mail column wraps `firstName` in `COALESCE`.

Hibernate ORM runs this as written. EclipseLink 5.0.1 passes `CAST(... AS STRING)` through to Oracle verbatim, which
rejects it (`+ORA-00902: invalid datatype+`); under EclipseLink, replace the cast with the Oracle function through
`+FUNCTION('TO_CHAR', e.employeeId)+` — standard JPQL syntax, but no longer database-neutral.

[[HR_EMPLOYEES_A_07]]
==== HR_EMPLOYEES_A_07: Pay against the department average

Before the pay review, each department head wants every member of staff next to the average salary of the department,
and how far above or below it they are.

[source,sql]
----
SELECT DEPARTMENT_ID, EMPLOYEE_ID, LAST_NAME, SALARY,
       ROUND(AVG(SALARY) OVER (PARTITION BY DEPARTMENT_ID), 2)          AS DEPARTMENT_AVERAGE,
       ROUND(SALARY - AVG(SALARY) OVER (PARTITION BY DEPARTMENT_ID), 2) AS DIFFERENCE
FROM EMPLOYEES
WHERE DEPARTMENT_ID IS NOT NULL
ORDER BY DEPARTMENT_ID ASC, SALARY DESC, EMPLOYEE_ID ASC
----

[source,jpaql]
----
SELECT e.department.departmentId, AVG(e.salary)
FROM Employee e
GROUP BY e.department.departmentId
----

`AVG(...) OVER (PARTITION BY ...)` is an aggregate that does not collapse the rows: every employee keeps their own row
and sees the average of their partition beside it. A `GROUP BY` gives the averages only, one row per department.
JPQL has no window functions, and its `SELECT` clause takes no subquery, so the JPQL fetches the averages per
department and the employees are matched to them in Java; or run the SQL as a native query. The single-person
departments, such as 10 (`Whalen`), show a difference of `0`.

== JOBS

=== Basic

[[HR_JOBS_B_01]]
==== HR_JOBS_B_01: Salary bands, unset values flagged

Compensation is reviewing the job catalogue. They want it twice: by minimum salary, lowest first, with any job that
has no minimum listed first; and by maximum salary, highest first, with any job that has no maximum listed last.

____
https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2#a5587[4.10. ORDER BY Clause]

The keyword `NULLS` specifies the ordering of null values, either `FIRST` or `LAST`.

* `FIRST` means that results are sorted so that all null values occur before all non-null values.

* `LAST` means that results are sorted so that all null values occur after all non-null values.

If `NULLS` is not specified, the database determines whether null values occur first or last.
____

[source,sql]
----
SELECT *
FROM JOBS
ORDER BY MIN_SALARY ASC NULLS FIRST, JOB_ID ASC
----

[source,jpaql]
----
SELECT j
FROM Job j
ORDER BY j.minSalary ASC NULLS FIRST, j.jobId ASC
----

[source,sql]
----
SELECT *
FROM JOBS
ORDER BY MAX_SALARY DESC NULLS LAST, JOB_ID ASC
----

[source,jpaql]
----
SELECT j
FROM Job j
ORDER BY j.maxSalary DESC NULLS LAST, j.jobId ASC
----

Every job in the installed data has both values, so the `NULLS` clauses decide nothing yet; they make the order
explicit for the day a job is added without a band. Oracle sorts nulls last ascending and first descending by default
— the opposite of what was asked here.

[[HR_JOBS_I_02]]
==== HR_JOBS_I_02: The catalogue at a glance

Workforce planning's summary of the job catalogue: how many jobs, the lowest minimum, the highest maximum, and the

[source,sql]

SELECT COUNT(*) AS JOBS, MIN(MIN_SALARY) AS LOWEST, MAX(MAX_SALARY) AS HIGHEST,

=== Advanced

[[HR_JOBS_A_01]]
==== HR_JOBS_A_01: Bands inside another band

Compensation suspects redundant grades: which jobs have a band that lies entirely within another job's band?

[source,sql]
----
SELECT i.JOB_ID, i.MIN_SALARY, i.MAX_SALARY,
       o.JOB_ID AS WITHIN_JOB, o.MIN_SALARY AS WITHIN_MIN, o.MAX_SALARY AS WITHIN_MAX
FROM JOBS i
         JOIN JOBS o ON o.JOB_ID <> i.JOB_ID
    AND o.MIN_SALARY <= i.MIN_SALARY
    AND i.MAX_SALARY <= o.MAX_SALARY

[source,jpaql]
----
SELECT i.jobId, i.minSalary, i.maxSalary, o.jobId, o.minSalary, o.maxSalary
FROM Job i,
     Job o
WHERE o <> i
  AND o.minSalary <= i.minSalary
  AND i.maxSalary <= o.maxSalary
ORDER BY i.jobId ASC, o.jobId ASC
----

Jobs with identical bands — `+AC_ACCOUNT+` and `+FI_ACCOUNT+`, `+AC_MGR+` and `+FI_MGR+`, `+PU_CLERK+` and `+SH_CLERK+` — each
lie within the other, so they appear in both directions.

[[HR_JOBS_A_02]]
==== HR_JOBS_A_02: The next step up

For career planning, HR wants, for each job, the job whose band starts lowest above the top of this job's band — the
next rung on the pay ladder.

[source,sql]
----
SELECT j.JOB_ID, j.MAX_SALARY, n.JOB_ID AS NEXT_JOB, n.MIN_SALARY AS NEXT_MIN
FROM JOBS j
         JOIN JOBS n ON n.MIN_SALARY = (SELECT MIN(x.MIN_SALARY) FROM JOBS x WHERE x.MIN_SALARY > j.MAX_SALARY)
ORDER BY j.MAX_SALARY ASC, j.JOB_ID ASC, n.JOB_ID ASC
----

[source,jpaql]
----
SELECT j.jobId, j.maxSalary, n.jobId, n.minSalary
FROM Job j,
     Job n
WHERE n.minSalary = (SELECT MIN(x.minSalary) FROM Job x WHERE x.minSalary > j.maxSalary)
ORDER BY j.maxSalary ASC, j.jobId ASC, n.jobId ASC
----

Jobs at the top of the ladder have no next step: the subquery returns null and the job drops out. Ties for the next
minimum are all reported.

[[HR_JOB_HISTORY_A_01]]
==== HR_JOB_HISTORY_A_01: Consecutive moves

Internal mobility wants each step recorded within the history: an earlier position, and the earlier position the same
employee held next — from which job to which, and when.

[source,sql]
----
SELECT EMPLOYEE_ID, FROM_JOB, TO_JOB, MOVED_ON
FROM (SELECT EMPLOYEE_ID, JOB_ID AS FROM_JOB,
             LEAD(JOB_ID) OVER (PARTITION BY EMPLOYEE_ID ORDER BY START_DATE)     AS TO_JOB,
             LEAD(START_DATE) OVER (PARTITION BY EMPLOYEE_ID ORDER BY START_DATE) AS MOVED_ON
      FROM JOB_HISTORY)
WHERE TO_JOB IS NOT NULL
ORDER BY EMPLOYEE_ID ASC, MOVED_ON ASC
----

[source,jpaql]
----
SELECT h.employeeId, h.job.jobId, n.job.jobId, n.startDate
FROM JobHistory h,
     JobHistory n
WHERE n.employeeId = h.employeeId
  AND n.startDate = (SELECT MIN(x.startDate)
                     FROM JobHistory x
                     WHERE x.employeeId = h.employeeId
                       AND x.startDate > h.startDate)
ORDER BY h.employeeId ASC, n.startDate ASC
----

position: the step from it into the current job needs `EMPLOYEES` (see _Career timeline of one employee_, under Whole

FROM JOB_HISTORY a
         JOIN JOB_HISTORY b ON b.EMPLOYEE_ID = a.EMPLOYEE_ID
    AND b.START_DATE > a.START_DATE
    AND b.START_DATE <= a.END_DATE
ORDER BY a.EMPLOYEE_ID ASC, a.START_DATE ASC

[source,jpaql]

     JobHistory b
WHERE b.employeeId = a.employeeId
  AND b.startDate > a.startDate
  AND b.startDate <= a.endDate

==== HR_SCHEMA_I_01: Headcount per department

HR wants every department with its headcount, largest first, including departments that have nobody.

[source,sql]
----

FROM DEPARTMENTS d
         LEFT JOIN EMPLOYEES e ON e.DEPARTMENT_ID = d.DEPARTMENT_ID

ORDER BY HEADCOUNT DESC, d.DEPARTMENT_ID ASC
----

[source,jpaql]
----

FROM Department d
         LEFT JOIN d.employees e
GROUP BY d.departmentId, d.departmentName
ORDER BY headcount DESC, d.departmentId ASC
----

[source,jpaql]

FROM Department d

an inner join and returns only the 11 departments that have staff. The `LEFT JOIN` form gives 27 under both.

[[HR_SCHEMA_A_02]]
==== HR_SCHEMA_A_02: Career timeline of one employee

An employee asks HR for their record: every position they have held, the current one included, in date order.
The schema records no start for the current position, so the exercise infers one: the day after the last `END_DATE` of the history, which the trigger writes when the job changes, or `HIRE_DATE` if there is none; the current one, with no end, comes last on a tie.

[source,sql]
----
SELECT h.START_DATE, h.END_DATE, h.JOB_ID, j.JOB_TITLE, h.DEPARTMENT_ID
FROM JOB_HISTORY h
         JOIN JOBS j ON j.JOB_ID = h.JOB_ID
WHERE h.EMPLOYEE_ID = :employeeId
UNION ALL
SELECT COALESCE((SELECT TRUNC(MAX(h2.END_DATE)) + 1 FROM JOB_HISTORY h2 WHERE h2.EMPLOYEE_ID = e.EMPLOYEE_ID), e.HIRE_DATE),
       NULL,
       e.JOB_ID,
       j.JOB_TITLE,
       e.DEPARTMENT_ID
FROM EMPLOYEES e
         JOIN JOBS j ON j.JOB_ID = e.JOB_ID
WHERE e.EMPLOYEE_ID = :employeeId
ORDER BY 1 ASC, 2 ASC NULLS LAST
----

[source,jpaql]
----
SELECT h.startDate, j.jobId, j.jobTitle
FROM JobHistory h
         JOIN h.job j
WHERE h.employeeId = :employeeId
UNION ALL
SELECT e.hireDate, j.jobId, j.jobTitle
FROM Employee e
         JOIN e.job j
WHERE e.employeeId = :employeeId
----

// JPQL NOT YET UPDATED: the SQL above changed.

`UNION`, `INTERSECT` and `EXCEPT` are new in Jakarta Persistence 3.2. The grammar attaches an `ORDER BY` to one
operand, not to the union as a whole, so sort the combined list in Java. The SQL's untyped `NULL` end date has no
portable JPQL counterpart either, and is left out. Read the result with care: `+HIRE_DATE+` is not moved when an
employee changes job, so the current position's start date is the original hire date, and for six of the employees
with history it is earlier than the end of their last recorded position (see the link:../../../README.md[README]).

[[HR_SCHEMA_A_05]]
==== HR_SCHEMA_A_05: Department roster in one round trip

The intranet's site page shows, for one location, each department and its staff, the empty departments included, the staff by last name, first name and `EMPLOYEE_ID`.
Loading the departments and then each one's employees is the N+1 problem; the page needs a single query, with each column named once.

[source,sql]
----
SELECT d.DEPARTMENT_ID, d.DEPARTMENT_NAME, e.EMPLOYEE_ID, e.FIRST_NAME, e.LAST_NAME, e.JOB_ID
FROM DEPARTMENTS d
         LEFT JOIN EMPLOYEES e ON e.DEPARTMENT_ID = d.DEPARTMENT_ID
WHERE d.LOCATION_ID = :locationId
ORDER BY d.DEPARTMENT_ID ASC, e.LAST_NAME ASC, e.FIRST_NAME ASC NULLS FIRST, e.EMPLOYEE_ID ASC
----

[source,jpaql]
----
SELECT DISTINCT d
FROM Department d
         LEFT JOIN FETCH d.employees
WHERE d.location.locationId = :locationId
ORDER BY d.departmentId ASC
----

// JPQL NOT YET UPDATED: the SQL above changed.

[source,jpaql]
----
SELECT e
FROM Employee e
         JOIN FETCH e.job
         LEFT JOIN FETCH e.department
WHERE e.department.departmentId = :departmentId
ORDER BY e.lastName ASC
----

Every association here is `LAZY`, so without `FETCH` each `getEmployees()` or `getJob()` call outside the query would

or cut a department's staff list short.

FROM Employee e
         LEFT JOIN FETCH e.job
         LEFT JOIN e.manager m1
         LEFT JOIN m1.manager m2
         LEFT JOIN m2.manager m3
WHERE e.employeeId = :employeeId
----

This walks the hierarchy the other way from _Everyone under a manager_ (under EMPLOYEES): `PRIOR` sits on the
manager's side, so each step goes from an employee to their manager, and the walk stops at the president, who has
none. Oracle joins `JOBS` first and walks the joined rows. For William Gietz (`206`) the chain is Gietz, Higgins,
Yang and King. JPQL is not recursive; the JPQL unrolls three steps up, enough for the installed data, and the `LEFT`
joins return `null` past the top. For any depth, follow `getManager()` from Java until it returns `null`, one lazy load
per step.

==== HR_SCHEMA_A_07: Each department's staff on one line

The intranet's department index shows each department with its headcount and its staff's last names on one line, alphabetically.
`LISTAGG ... WITHIN GROUP (ORDER BY ...)` joins the names in order.

[source,sql]
----
SELECT d.DEPARTMENT_ID,
       d.DEPARTMENT_NAME,
       COUNT(*)                                                                          AS HEADCOUNT,
       LISTAGG(e.LAST_NAME, ', ') WITHIN GROUP (ORDER BY e.LAST_NAME, e.EMPLOYEE_ID) AS STAFF
FROM DEPARTMENTS d
         JOIN EMPLOYEES e ON e.DEPARTMENT_ID = d.DEPARTMENT_ID
GROUP BY d.DEPARTMENT_ID, d.DEPARTMENT_NAME
ORDER BY d.DEPARTMENT_ID ASC
----
