= Exercises
:toc: left
:toclevels: 3
:sectanchors:
:source-highlighter: rouge

Exercises for the Customer Orders (CO) schema: business questions that a store manager, a merchandiser, logistics,
marketing or finance would ask of a small retail chain, each answered with a query. Every problem is stated as a
request, followed by one or more solutions. The `sql` blocks are Oracle SQL against the installed schema
(see link:../../../README.md[README.md]), with `:name` bind variables. The `jpaql` blocks are Jakarta Persistence 3.2 query
language against this module's entities -- `Customer`, `Store`, `Product`, `Order`, `OrderItem`,
`Shipment`, `Inventory`, and the views `CustomerOrderProduct` and `ProductOrder` -- with named
parameters of the same names.

The problems are grouped by what they read. Each table and view of the schema has a section, in the order of
link:../../../README.md[README.md], holding the problems whose SQL reads that one object -- a self-join or a subquery on it
included. _Whole schema_, the last section, holds the problems that join or subquery more than one. Every section
goes from Basic through Intermediate to Advanced.

A few things about the mappings shape the JPQL below:

* A foreign key is mapped twice: as an association on the entity, and as a read-only attribute on its mapped
  superclass. `Order` has `customer` and `store`, and `customerId`/`storeId` from `MappedOrder`. The answers below
  reach a key as `o.customer.customerId`, or compare the entity itself: `+o.customer = :customer+`.
* `+ORDERS.ORDER_STATUS+` is `MappedOrder.OrderStatus`, mapped `+@Enumerated(EnumType.STRING)+`. Compare it with an
  enum parameter or a fully qualified enum literal, never with a string. The literal names the class that declares the
  enum, `+com.github.jinahya.oracle.sample.persistence.co.mapped.MappedOrder.OrderStatus+`, not `Order`.
* `+SHIPMENTS.SHIPMENT_STATUS+` is `MappedShipment.ShipmentStatus`, mapped through `ShipmentStatusConverter`, because the
  column holds `+IN-TRANSIT+` and the constant is `+IN_TRANSIT+`. Bind the enum as a parameter.
* `Order.orderItems` is a `+Map<Product, OrderItem>+` keyed by each item's product,
  `+@MapKey(name = OrderItem.ATTRIBUTE_NAME_PRODUCT)+`. The queries below start from `OrderItem` and navigate
  `oi.order`, or join it to an order with a Jakarta Persistence 3.2 entity join, `+JOIN OrderItem oi ON oi.order = o+`.
* `OrderItem` maps `+ORDER_ITEMS+` with an `+@EmbeddedId+`, `OrderItemId`, so its key is `oi.id.orderId` and
  `oi.id.lineItemId`. `ProductOrder` maps `+PRODUCT_ORDERS+` with an `+@EmbeddedId+`, so its key is
  `v.id.productName` and `v.id.orderStatus`.
* `+STORE_ORDERS+` and `+PRODUCT_REVIEWS+` are not entities (`StoreOrder`, `ProductReview`), and
  `+PRODUCTS.PRODUCT_DETAILS+` is a JSON document mapped as a `+byte[]+` LOB. Queries over them are SQL only, and the
  note says how to approach them from Jakarta Persistence.

== CUSTOMERS

=== Basic

[[CO_CUSTOMERS_B_01]]
==== CO_CUSTOMERS_B_01: Pull up a customer by email address

The support desk has a caller who gives their email address. Find the customer account for it.

[source,sql]
----
SELECT customer_id, email_address, full_name
FROM customers
WHERE email_address = :emailAddress
----

[source,jpaql]
----
SELECT c
FROM Customer c
WHERE c.emailAddress = :emailAddress
----

`+EMAIL_ADDRESS+` is unique, so `getSingleResult()` fits; it throws `NoResultException` for an unknown address.

[[CO_CUSTOMERS_B_02]]
==== CO_CUSTOMERS_B_02: Search customers by the start of their name

The caller's name was only half heard. List the customers whose full name starts with the given text, ignoring case,
in alphabetical order.

[source,sql]
----
SELECT customer_id, full_name, email_address
FROM customers
WHERE UPPER(full_name) LIKE UPPER(:prefix) || '%'
ORDER BY full_name
----

[source,jpaql]
----
SELECT c
FROM Customer c
WHERE UPPER(c.fullName) LIKE :pattern
ORDER BY c.fullName
----

A JPQL `LIKE` pattern must be a string literal or an input parameter, so the pattern is built in Java:
`+prefix.toUpperCase() + "%"+`. Escape `+%+` and `+_+` in the prefix (with an `ESCAPE` clause) if users may type them.

=== Intermediate

[[CO_CUSTOMERS_I_01]]
==== CO_CUSTOMERS_I_01: Email addresses that break the house style

Accounts are meant to be opened as `first.last@...`.
Data quality wants the customers whose email address, before the `@`, is not their full name in lower case with the spaces turned into dots, including the addresses with nothing before an `@` or no `@` at all; customers with the same name are ordered by `customer_id`.

[source,sql]
----
SELECT customer_id, full_name, email_address
FROM customers
WHERE INSTR(email_address, '@') <= 1
   OR SUBSTR(email_address, 1, INSTR(email_address, '@') - 1) <> LOWER(REPLACE(full_name, ' ', '.'))
ORDER BY full_name, customer_id
----

[source,jpaql]
----
SELECT c
FROM Customer c
WHERE SUBSTRING(c.emailAddress, 1, LOCATE('@', c.emailAddress) - 1) <> LOWER(REPLACE(c.fullName, ' ', '.'))
ORDER BY c.fullName
----

// JPQL NOT YET UPDATED: the SQL above changed.

The result is a list to review, not a list of mistakes: a customer with a middle name, such as `Norman Simon Lobregat`
at `+norman.s.lobregat@...+`, is reported too.

=== Advanced

[[CO_CUSTOMERS_A_01]]
==== CO_CUSTOMERS_A_01: Possible duplicate accounts

Before a mailing, marketing wants pairs of accounts that may belong to one person: the same name, ignoring case and
surrounding spaces, or the same email address before the `+@+` at a different domain.

[source,sql]
----
SELECT a.customer_id, a.full_name, a.email_address,
       b.customer_id AS other_customer_id, b.full_name AS other_full_name, b.email_address AS other_email_address
FROM customers a
         JOIN customers b ON b.customer_id > a.customer_id
WHERE UPPER(TRIM(b.full_name)) = UPPER(TRIM(a.full_name))
   OR SUBSTR(b.email_address, 1, INSTR(b.email_address, '@') - 1)
          = SUBSTR(a.email_address, 1, INSTR(a.email_address, '@') - 1)
ORDER BY a.customer_id, b.customer_id
----

[source,jpaql]
----
SELECT a, b
FROM Customer a
         JOIN Customer b ON b.customerId > a.customerId
WHERE UPPER(TRIM(b.fullName)) = UPPER(TRIM(a.fullName))
   OR SUBSTRING(b.emailAddress, 1, LOCATE('@', b.emailAddress) - 1)
          = SUBSTRING(a.emailAddress, 1, LOCATE('@', a.emailAddress) - 1)
ORDER BY a.customerId, b.customerId
----

`+b.customer_id > a.customer_id+` reports each pair once and never pairs an account with itself. The installed data has
no such pair, so the answer is empty.

== CUSTOMER_ORDER_PRODUCTS

`+CUSTOMER_ORDER_PRODUCTS+` has one row per order, with the customer's name and email address, the order's total, and
its product names in `ITEMS`. `CustomerOrderProduct` maps it as a read-only entity whose `orderStatus` is a `String`.

=== Basic

[[CO_CUSTOMER_ORDER_PRODUCTS_B_02]]
==== CO_CUSTOMER_ORDER_PRODUCTS_B_02: Review a customer's completed baskets

Customer care wants a customer's completed orders, each with its total and the summary of its products, the most recent first.

[source,sql]
----
SELECT order_id, order_tms, order_total, items
FROM customer_order_products
WHERE customer_id = :customerId
  AND order_status = 'COMPLETE'
ORDER BY order_tms DESC, order_id DESC
----


=== Intermediate

[[CO_CUSTOMER_ORDER_PRODUCTS_I_01]]
==== CO_CUSTOMER_ORDER_PRODUCTS_I_01: Average basket per customer

Marketing wants, per customer, the number of completed orders, what they came to and the average order value, the
biggest spenders first.

[source,sql]
----
SELECT customer_id, full_name, COUNT(*) AS orders, SUM(order_total) AS total_spent,
       ROUND(AVG(order_total), 2) AS average_order
FROM customer_order_products
WHERE order_status = 'COMPLETE'
GROUP BY customer_id, full_name
ORDER BY total_spent DESC, full_name
----

[source,jpaql]
----
SELECT v.customerId, v.fullName, COUNT(v), SUM(v.orderTotal), AVG(v.orderTotal)
FROM CustomerOrderProduct v
WHERE v.orderStatus = 'COMPLETE'
GROUP BY v.customerId, v.fullName
ORDER BY SUM(v.orderTotal) DESC, v.fullName
----

The view's `orderStatus` is a `String`, so a string literal is right here, unlike for `Order.orderStatus`.

=== Advanced

[[CO_CUSTOMER_ORDER_PRODUCTS_A_01]]
==== CO_CUSTOMER_ORDER_PRODUCTS_A_01: Each customer's biggest order

For a thank-you letter, marketing wants each customer's most valuable order. A tie gives a customer more than one row.

[source,sql]
----
SELECT customer_id, full_name, order_id, order_tms, order_total
FROM (SELECT v.*, RANK() OVER (PARTITION BY v.customer_id ORDER BY v.order_total DESC) AS rnk
      FROM customer_order_products v)
WHERE rnk = 1
ORDER BY order_total DESC, full_name
----

[source,jpaql]
----
SELECT v
FROM CustomerOrderProduct v
WHERE v.orderTotal = (SELECT MAX(v2.orderTotal)
                      FROM CustomerOrderProduct v2
                      WHERE v2.customerId = v.customerId)
ORDER BY v.orderTotal DESC, v.fullName
----

JPQL has no window functions; a correlated subquery takes the maximum per customer instead. The view aggregates
`+ORDER_ITEMS+` on every read, so the subquery form evaluates it again for each row; the `RANK()` form reads it once.

== INVENTORY

=== Basic

[[CO_INVENTORY_B_01]]
==== CO_INVENTORY_B_01: How many are on the shelf?

A shop assistant asks how many units of a product their store holds.

[source,sql]
----
SELECT product_inventory
FROM inventory
WHERE store_id = :storeId
  AND product_id = :productId
----

[source,jpaql]
----
SELECT i.productInventory
FROM Inventory i
WHERE i.store.storeId = :storeId
  AND i.product.productId = :productId
----

[source,jpaql]
----
SELECT e
FROM Inventory AS e
WHERE e.store = :store AND e.product = :product
----

`+(STORE_ID, PRODUCT_ID)+` is unique, so there is at most one row. No row means the store does not stock the product at
all, which is not the same as a stock of `0`. The second JPQL form takes the `Store` and the `Product` themselves and
selects the whole `Inventory`.

[[CO_INVENTORY_B_02]]
==== CO_INVENTORY_B_02: Where a product is running lowest

A merchandiser wants every store's stock of a product, lowest first, to see which stores need it replenished first; stores with the same stock are ordered by `store_id`.

[source,sql]
----
SELECT store_id, product_inventory
FROM inventory
WHERE product_id = :productId
ORDER BY product_inventory, store_id
----

[source,jpaql]
----
SELECT e
FROM Inventory AS e
WHERE e.product = :product
ORDER BY e.productInventory ASC
----

// JPQL NOT YET UPDATED: the SQL above changed.

A product is stocked at many stores, so the JPQL returns a list -- one row per store. Stores with the same stock come
back in no particular order; add `e.store.storeId` to the `ORDER BY` for a stable order.

[[CO_INVENTORY_B_04]]
==== CO_INVENTORY_B_04: Negative stock

Nothing in the schema keeps `PRODUCT_INVENTORY` from going below `0`, which the replenishment exercises assume.
Find the inventory rows with a negative stock, the most negative first; the check passes when nothing comes back.

[source,sql]
----
SELECT inventory_id, store_id, product_id, product_inventory
FROM inventory
WHERE product_inventory < 0
ORDER BY product_inventory, store_id, product_id
----


=== Intermediate

[[CO_INVENTORY_I_01]]
==== CO_INVENTORY_I_01: What each store holds

The regional manager wants, per store, how many products it stocks, how many units it holds in all, and how many of its
products are down to zero.

[source,sql]
----
SELECT store_id, COUNT(*) AS products, SUM(product_inventory) AS units,
       COUNT(CASE WHEN product_inventory = 0 THEN 1 END) AS empty_shelves
FROM inventory
GROUP BY store_id
ORDER BY store_id
----

[source,jpaql]
----
SELECT i.store.storeId, COUNT(i), SUM(i.productInventory),
       SUM(CASE WHEN i.productInventory = 0 THEN 1 ELSE 0 END)
FROM Inventory i
GROUP BY i.store.storeId
ORDER BY i.store.storeId
----

`i.store.storeId` is the foreign key itself, so no join to `STORES` is needed; the store's name does need one (see
_Running low_). The 3.2 grammar gives `SUM` a path argument only; both providers accept an expression, as they do for
`+unitPrice * quantity+` elsewhere in this file.

=== Advanced

[[CO_INVENTORY_A_01]]
==== CO_INVENTORY_A_01: Stores that carry everything another store carries

A store is closing for a refit. The regional manager wants the stores that carry every product it carries, to send its
customers to.

[source,sql]
----
SELECT DISTINCT i.store_id
FROM inventory i
WHERE i.store_id <> :storeId
  AND NOT EXISTS (SELECT 1
                  FROM inventory r
                  WHERE r.store_id = :storeId
                    AND NOT EXISTS (SELECT 1
                                    FROM inventory x
                                    WHERE x.store_id = i.store_id
                                      AND x.product_id = r.product_id))
ORDER BY i.store_id
----

[source,jpaql]
----
SELECT DISTINCT i.store.storeId
FROM Inventory i
WHERE i.store.storeId <> :storeId
  AND NOT EXISTS (SELECT r
                  FROM Inventory r
                  WHERE r.store.storeId = :storeId
                    AND NOT EXISTS (SELECT x
                                    FROM Inventory x
                                    WHERE x.store = i.store
                                      AND x.product = r.product))
ORDER BY i.store.storeId
----

This is relational division, written as a double negative: a store qualifies when there is no product of the closing
store that it lacks. A row counts as "carried" even at a stock of `0`; add `+AND x.productInventory > 0+` to require stock
on the shelf. Store 1 (`Online`) carries all 46 products, so no other store qualifies for it; for store 20 the answer
is stores 1, 4, 9, 10, 14 and 19.

== ORDERS

=== Basic

[[CO_ORDERS_B_01]]
==== CO_ORDERS_B_01: A customer's order history

Show all of a customer's orders, the most recent first; orders placed at the same moment are ordered by `order_id`, the highest first.

[source,sql]
----
SELECT order_id, order_tms, order_status, store_id
FROM orders
WHERE customer_id = :customerId
ORDER BY order_tms DESC, order_id DESC
----

[source,jpaql]
----
SELECT o
FROM Order o
WHERE o.customer.customerId = :customerId
ORDER BY o.orderTms DESC
----

// JPQL NOT YET UPDATED: the SQL above changed.

[source,jpaql]
----
SELECT o
FROM Order o
WHERE o.customer = :customer
ORDER BY o.orderTms DESC
----

`o.customer.customerId` is the association's own key, so it needs no join to `CUSTOMERS`. The second form binds a
`Customer` (a reference from `getReference` is enough).

[[CO_ORDERS_B_02]]
==== CO_ORDERS_B_02: Orders that went wrong

Finance reviews every order that was cancelled or refunded, newest first.

[source,sql]
----
SELECT order_id, order_tms, order_status, customer_id, store_id
FROM orders
WHERE order_status IN ('CANCELLED', 'REFUNDED')
ORDER BY order_tms DESC
----

[source,jpaql]
----
SELECT o
FROM Order o
WHERE o.orderStatus IN :statuses
ORDER BY o.orderTms DESC
----

[source,jpaql]
----
SELECT o
FROM Order o
WHERE o.orderStatus IN (com.github.jinahya.oracle.sample.persistence.co.mapped.MappedOrder.OrderStatus.CANCELLED,
                        com.github.jinahya.oracle.sample.persistence.co.mapped.MappedOrder.OrderStatus.REFUNDED)
ORDER BY o.orderTms DESC
----

`:statuses` is a `+List<Order.OrderStatus>+`. An enum literal in JPQL is the constant's fully qualified name; a string
such as `+'CANCELLED'+` is not comparable with an enum attribute.

[[CO_ORDERS_B_03]]
==== CO_ORDERS_B_03: A store's orders for a period

A store manager wants the orders taken at their store during a period: on or after `:fromTms`, and before `:toTms`.

[source,sql]
----
SELECT order_id, order_tms, order_status, customer_id
FROM orders
WHERE store_id = :storeId
  AND order_tms >= :fromTms
  AND order_tms < :toTms
ORDER BY order_tms
----

[source,jpaql]
----
SELECT o
FROM Order o
WHERE o.store.storeId = :storeId
  AND o.orderTms >= :fromTms
  AND o.orderTms < :toTms
ORDER BY o.orderTms
----

`+ORDER_TMS+` is a `TIMESTAMP`, mapped as `LocalDateTime`. A half-open range lets consecutive periods meet without
overlapping; `BETWEEN` includes both ends, so an order at exactly `:toTms` would be counted in two periods.

[[CO_ORDERS_B_04]]
==== CO_ORDERS_B_04: The next page of a customer's order history

The account page shows a customer's orders `:pageSize` at a time, the most recent first.
Show the page that starts after the first `:offset` orders; `order_id` breaks a tie, so a page neither repeats nor skips an order.

[source,sql]
----
SELECT order_id, order_tms, order_status, store_id
FROM orders
WHERE customer_id = :customerId
ORDER BY order_tms DESC, order_id DESC
OFFSET :offset ROWS FETCH NEXT :pageSize ROWS ONLY
----


=== Intermediate

[[CO_ORDERS_I_01]]
==== CO_ORDERS_I_01: Where orders stand

Operations wants the number of orders in each status, with the first and the last order placed in it.

[source,sql]
----
SELECT order_status, COUNT(*) AS orders, MIN(order_tms) AS first_order_tms, MAX(order_tms) AS last_order_tms
FROM orders
GROUP BY order_status
ORDER BY orders DESC
----

[source,jpaql]
----
SELECT o.orderStatus, COUNT(o), MIN(o.orderTms), MAX(o.orderTms)
FROM Order o
GROUP BY o.orderStatus
ORDER BY COUNT(o) DESC
----

Only the statuses that occur are returned: the installed orders are all `COMPLETE`, `CANCELLED` or `REFUNDED`. To show
all six with zeros, iterate `Order.OrderStatus.values()` in Java and fill in the counts.

=== Advanced

[[CO_ORDERS_A_01]]
==== CO_ORDERS_A_01: Customers of two stores, or of one only

Two store managers plan a joint promotion. Marketing wants (a) the customers who have ordered from both stores,
(b) those who ordered from the first store but never from the second, and (c) everyone who ordered from either.

[source,sql]
----
SELECT customer_id FROM orders WHERE store_id = :storeA
INTERSECT
SELECT customer_id FROM orders WHERE store_id = :storeB
----

[source,jpaql]
----
SELECT o.customer.customerId FROM Order o WHERE o.store.storeId = :storeA
INTERSECT
SELECT o.customer.customerId FROM Order o WHERE o.store.storeId = :storeB
----

[source,sql]
----
SELECT customer_id FROM orders WHERE store_id = :storeA
MINUS
SELECT customer_id FROM orders WHERE store_id = :storeB
----

[source,jpaql]
----
SELECT o.customer.customerId FROM Order o WHERE o.store.storeId = :storeA
EXCEPT
SELECT o.customer.customerId FROM Order o WHERE o.store.storeId = :storeB
----

[source,sql]
----
SELECT customer_id FROM orders WHERE store_id = :storeA
UNION
SELECT customer_id FROM orders WHERE store_id = :storeB
----

[source,jpaql]
----
SELECT o.customer.customerId FROM Order o WHERE o.store.storeId = :storeA
UNION
SELECT o.customer.customerId FROM Order o WHERE o.store.storeId = :storeB
----

`UNION`, `INTERSECT` and `EXCEPT` are new in Jakarta Persistence 3.2. Oracle's traditional spelling of `EXCEPT` is
`MINUS`; 21c and later accept `EXCEPT` as well. Without `ALL` they remove duplicates, as in SQL.

[[CO_ORDERS_A_02]]
==== CO_ORDERS_A_02: Time between a customer's orders

Customer care, looking at one customer, wants each of their orders next to the one before it, and the whole days between the two, to see how often they come back; orders placed at the same moment are ordered by `order_id`.

[source,sql]
----
SELECT order_id,
       order_tms,
       previous_order_tms,
       EXTRACT(DAY FROM order_tms - previous_order_tms) AS days_since_previous
FROM (SELECT order_id, order_tms, LAG(order_tms) OVER (ORDER BY order_tms, order_id) AS previous_order_tms
      FROM orders
      WHERE customer_id = :customerId)
ORDER BY order_tms, order_id
----

[source,jpaql]
----
SELECT o.orderId, o.orderTms,
       (SELECT MAX(p.orderTms) FROM Order p WHERE p.customer = o.customer AND p.orderTms < o.orderTms)
FROM Order o
WHERE o.customer.customerId = :customerId
ORDER BY o.orderTms
----

// JPQL NOT YET UPDATED: the SQL above changed.

Without `LAG()`, the previous order is the latest one placed before this one, a correlated subquery in the select list;
it is null for the first order. Subtracting two ``TIMESTAMP``s gives an `INTERVAL DAY TO SECOND` in Oracle; in Java, take
`Duration.between(previous, current).toDays()`.

[[CO_ORDERS_A_03]]
==== CO_ORDERS_A_03: New and returning customers by month

Marketing wants to know whether the store still wins new customers or lives on its regulars: per month, how many
orders were a customer's first order and how many came from a customer who had ordered before.

[source,sql]
----
SELECT TO_CHAR(order_tms, 'YYYY-MM') AS order_month,
       COUNT(CASE WHEN rn = 1 THEN 1 END) AS first_orders,
       COUNT(CASE WHEN rn > 1 THEN 1 END) AS repeat_orders
FROM (SELECT order_tms,
             ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY order_tms, order_id) AS rn
      FROM orders)
GROUP BY TO_CHAR(order_tms, 'YYYY-MM')
ORDER BY order_month
----

[source,jpaql]
----
SELECT o
FROM Order o
WHERE NOT EXISTS (SELECT p
                  FROM Order p
                  WHERE p.customer = o.customer
                    AND (p.orderTms < o.orderTms
                         OR (p.orderTms = o.orderTms AND p.orderId < o.orderId)))
ORDER BY o.orderTms
----

`ROW_NUMBER()` numbers each customer's orders in time; the first is number 1, whatever month it falls in. `order_id`
breaks a tie between two orders placed at the same moment, so a customer never has two first orders. JPQL has no window
functions; the JPQL selects each customer's first order with a correlated `NOT EXISTS` instead, and the rest of the
month's orders are the repeat ones. Counting both per month is then done in Java, or with `EXTRACT(YEAR FROM
o.orderTms)` and `EXTRACT(MONTH FROM o.orderTms)` in a `GROUP BY` over the same condition. In the installed data the 392
customers who ordered place 15 first orders in February 2021 against 3 repeat ones; from March 2022 on, every order is
a repeat one.

== ORDER_ITEMS

`+ORDER_ITEMS+` is queried through `OrderItem` (see the note on `Order.orderItems` above); its order and
line number are `oi.id.orderId` and `oi.id.lineItemId`.

=== Basic

[[CO_ORDER_ITEMS_B_01]]
==== CO_ORDER_ITEMS_B_01: Bulk lines

Fraud prevention watches for bulk buying. List the order lines of `:minQuantity` units or more, the largest first.

[source,sql]
----
SELECT order_id, line_item_id, product_id, unit_price, quantity
FROM order_items
WHERE quantity >= :minQuantity
ORDER BY quantity DESC, order_id, line_item_id
----

[source,jpaql]
----
SELECT oi
FROM OrderItem oi
WHERE oi.quantity >= :minQuantity
ORDER BY oi.quantity DESC, oi.id.orderId, oi.id.lineItemId
----

No line of the installed data has more than five units.

=== Intermediate

[[CO_ORDER_ITEMS_I_01]]
==== CO_ORDER_ITEMS_I_01: Orders worth more than an amount

Fraud prevention also reviews every order worth more than `:amount`, with its number of lines and units, from the
lines alone.

[source,sql]
----
SELECT order_id, COUNT(*) AS lines, SUM(quantity) AS units, SUM(unit_price * quantity) AS order_total
FROM order_items
GROUP BY order_id
HAVING SUM(unit_price * quantity) > :amount
ORDER BY order_total DESC
----

[source,jpaql]
----
SELECT oi.id.orderId, COUNT(oi), SUM(oi.quantity), SUM(oi.unitPrice * oi.quantity)
FROM OrderItem oi
GROUP BY oi.id.orderId
HAVING SUM(oi.unitPrice * oi.quantity) > :amount
ORDER BY SUM(oi.unitPrice * oi.quantity) DESC
----

Grouping by `oi.id.orderId`, the key column, rather than by `oi.order` keeps the query on `+ORDER_ITEMS+` alone.

[[CO_ORDER_ITEMS_I_02]]
==== CO_ORDER_ITEMS_I_02: Orders with gaps in their line numbers

The schema describes `LINE_ITEM_ID` as a number starting at one for each order, but does not enforce it.
Data quality wants the orders whose line numbers do not run 1, 2, 3, ... without gaps, with their number of lines and their first and last line number; the check passes when nothing comes back.

[source,sql]
----
SELECT order_id, COUNT(*) AS lines, MIN(line_item_id) AS first_line, MAX(line_item_id) AS last_line
FROM order_items
GROUP BY order_id
HAVING MIN(line_item_id) <> 1
    OR MAX(line_item_id) <> COUNT(*)
ORDER BY order_id
----


=== Advanced

[[CO_ORDER_ITEMS_A_01]]
==== CO_ORDER_ITEMS_A_01: Each order's main line

Customer care settles a complaint about an order against its main line: the line with the largest value. List it for
every order; a tie gives an order more than one row.

[source,sql]
----
SELECT order_id, line_item_id, product_id, unit_price * quantity AS line_total
FROM (SELECT oi.*, RANK() OVER (PARTITION BY oi.order_id ORDER BY oi.unit_price * oi.quantity DESC) AS rnk
      FROM order_items oi)
WHERE rnk = 1
ORDER BY order_id, line_item_id
----

[source,jpaql]
----
SELECT oi.id.orderId, oi.id.lineItemId, oi.product.productId, oi.unitPrice * oi.quantity
FROM OrderItem oi
WHERE oi.unitPrice * oi.quantity >= ALL (SELECT oi2.unitPrice * oi2.quantity
                                         FROM OrderItem oi2
                                         WHERE oi2.id.orderId = oi.id.orderId)
ORDER BY oi.id.orderId, oi.id.lineItemId
----

`+>= ALL+` over the order's own lines stands in for `RANK()`; the subquery is never empty, because it contains the line
itself.

[[CO_PRODUCT_ORDERS_I_01]]

=== Advanced

[[CO_PRODUCT_ORDERS_A_01]]
==== CO_PRODUCT_ORDERS_A_01: Products that are often cancelled or refunded

Quality assurance wants the products whose cancelled and refunded orders make up more than `:percent` per cent (say
5) of all their orders, with both counts.

[source,sql]
----
SELECT product_name,
       SUM(order_count) AS orders,
       SUM(CASE WHEN order_status IN ('CANCELLED', 'REFUNDED') THEN order_count ELSE 0 END) AS lost_orders,
       ROUND(100 * SUM(CASE WHEN order_status IN ('CANCELLED', 'REFUNDED') THEN order_count ELSE 0 END)
                 / SUM(order_count), 1) AS lost_pct
FROM product_orders
GROUP BY product_name
HAVING SUM(CASE WHEN order_status IN ('CANCELLED', 'REFUNDED') THEN order_count ELSE 0 END)
           * 100 > :percent * SUM(order_count)
ORDER BY lost_pct DESC, product_name
----

[source,jpaql]
----
SELECT v.id.productName,
       SUM(v.orderCount),
       SUM(CASE WHEN v.id.orderStatus IN ('CANCELLED', 'REFUNDED') THEN v.orderCount ELSE 0 END)
FROM ProductOrder v
GROUP BY v.id.productName
HAVING SUM(CASE WHEN v.id.orderStatus IN ('CANCELLED', 'REFUNDED') THEN v.orderCount ELSE 0 END)
           * 100 > :percent * SUM(v.orderCount)
ORDER BY v.id.productName
----

A `CASE` inside `SUM` counts a subset of the rows of a group, which `WHERE` cannot do without losing the total. The 3.2
grammar gives `SUM` a path argument only; both providers accept the `CASE`. Work out the percentage in Java. The
comparison is kept in whole numbers: Hibernate types `:percent` after `SUM(v.orderCount)`, a `Long`, and refuses a
fractional share such as `0.05`.

`+PRODUCT_REVIEWS+` turns the `reviews` array of each product's JSON into rows. `ProductReview` is a plain class, not an

=== Intermediate

[[CO_PRODUCT_REVIEWS_I_01]]
==== CO_PRODUCT_REVIEWS_I_01: Products with mostly poor reviews

Quality assurance wants the products where more than half of the reviews give 3 or less, with the number of each.

[source,sql]

       COUNT(rating) AS reviews,
       COUNT(CASE WHEN rating <= 3 THEN 1 END) AS poor_reviews

=== Advanced

[[CO_PRODUCT_REVIEWS_A_01]]
==== CO_PRODUCT_REVIEWS_A_01: Each product's harshest review

Before a supplier meeting, the buyer wants the lowest-rated review of every product, and how far it falls below the
product's average.

[source,sql]
----
SELECT product_name, rating, avg_rating, avg_rating - rating AS below_average, review
FROM (SELECT r.*, ROW_NUMBER() OVER (PARTITION BY r.product_name ORDER BY r.rating, r.review) AS rn
      FROM product_reviews r
      WHERE r.rating IS NOT NULL)
WHERE rn = 1
ORDER BY below_average DESC, product_name
----

=== Advanced

[[CO_STORES_A_01]]
==== CO_STORES_A_01: Each store's nearest neighbour

For each store with both coordinates, show its nearest other store with both coordinates, all of them at a tie, and the great-circle distance in kilometres.

[source,sql]
----
WITH distances AS (SELECT s.store_id,
                          s.store_name,
                          n.store_name AS nearest_store,
                          6371 * ACOS(GREATEST(-1, LEAST(1,
                              SIN(s.latitude * ACOS(-1) / 180) * SIN(n.latitude * ACOS(-1) / 180)
                              + COS(s.latitude * ACOS(-1) / 180) * COS(n.latitude * ACOS(-1) / 180)
                                * COS((s.longitude - n.longitude) * ACOS(-1) / 180)))) AS km
                   FROM stores s
                            JOIN stores n ON n.store_id <> s.store_id
                   WHERE s.latitude IS NOT NULL
                     AND s.longitude IS NOT NULL
                     AND n.latitude IS NOT NULL
                     AND n.longitude IS NOT NULL)
SELECT store_name, nearest_store, ROUND(km, 2) AS km
FROM (SELECT d.*, RANK() OVER (PARTITION BY store_id ORDER BY km) AS rnk FROM distances d)
WHERE rnk = 1
ORDER BY store_name, nearest_store
----

[source,jpaql]
----
SELECT s.storeName, n.storeName,
       SQRT(POWER(n.latitude - s.latitude, 2) + POWER(n.longitude - s.longitude, 2))
FROM Store s
         JOIN Store n ON n.storeId <> s.storeId
WHERE s.latitude IS NOT NULL
  AND n.latitude IS NOT NULL
  AND POWER(n.latitude - s.latitude, 2) + POWER(n.longitude - s.longitude, 2)
      = (SELECT MIN(POWER(m.latitude - s.latitude, 2) + POWER(m.longitude - s.longitude, 2))
         FROM Store m
         WHERE m.storeId <> s.storeId)
ORDER BY s.storeName
----

// JPQL NOT YET UPDATED: the SQL above changed.

The distance is measured in degrees on a flat map, which is crude: a degree of longitude shrinks towards the poles,
and the map does not wrap at 180°. It is enough to find a neighbour, not to quote kilometres; in SQL, the haversine
formula (`SIN`, `COS`, `ACOS`) gives the great-circle distance, and JPQL has no trigonometric functions. `MIN` skips the
online store, whose coordinates are null. `POWER` and `SQRT` are 3.2 additions.

=== Advanced

[[CO_STORE_ORDERS_A_01]]
==== CO_STORE_ORDERS_A_01: Each store's losses against its own sales and the chain's

For every store with a store-total row, show its cancelled and refunded sales, `0` where it has none, and their share of the store's sales and of the chain's, every status counted; a share is NULL where its total is `0`.

[source,sql]
----
SELECT st.store_name,
       COALESCE(SUM(d.total_sales), 0)                                                 AS lost_sales,
       ROUND(100 * COALESCE(SUM(d.total_sales), 0) / NULLIF(MAX(st.total_sales), 0), 1) AS pct_of_store,
       ROUND(100 * COALESCE(SUM(d.total_sales), 0) / NULLIF(MAX(g.total_sales), 0), 2)  AS pct_of_chain
FROM store_orders st
         LEFT JOIN store_orders d ON d.store_name = st.store_name
    AND d.total IS NULL
    AND d.order_status IN ('CANCELLED', 'REFUNDED')
         CROSS JOIN (SELECT total_sales FROM store_orders WHERE total = 'GRAND TOTAL') g
WHERE st.total = 'STORE TOTAL'
GROUP BY st.store_name
ORDER BY pct_of_store DESC NULLS LAST, st.store_name
----

All three figures come from the one view: the detail rows, the store's `STORE TOTAL` row and the `GRAND TOTAL` row.
`MAX` only carries the single store and chain totals through the `GROUP BY`. Each reference to the view computes its
`GROUPING SETS` again; over the base tables, `+RATIO_TO_REPORT+` gives the same in one pass.

==== CO_SCHEMA_A_04: Each store's best seller

Each store manager wants to know their store's best-selling product by units, over all orders. A tie gives a store

[source,sql]
----
SELECT store_name, product_name, units_sold
FROM (SELECT s.store_name, p.product_name, SUM(oi.quantity) AS units_sold,
             RANK() OVER (PARTITION BY s.store_id ORDER BY SUM(oi.quantity) DESC) AS rnk
      FROM stores s
               JOIN orders o ON o.store_id = s.store_id
               JOIN order_items oi ON oi.order_id = o.order_id
               JOIN products p ON p.product_id = oi.product_id
      GROUP BY s.store_id, s.store_name, p.product_id, p.product_name)
WHERE rnk = 1
ORDER BY store_name, product_name
----

[source,jpaql]
----
SELECT s.storeName, p.productName, SUM(oi.quantity)
FROM OrderItem oi
         JOIN oi.order o
         JOIN o.store s
         JOIN oi.product p
GROUP BY s.storeId, s.storeName, p.productId, p.productName
HAVING SUM(oi.quantity) >= ALL (SELECT SUM(oi2.quantity)
                                FROM OrderItem oi2
                                WHERE oi2.order.store.storeId = s.storeId
                                GROUP BY oi2.product.productId)
ORDER BY s.storeName, p.productName
----

JPQL has no window functions. `+>= ALL+` over a correlated, grouped subquery gives the top 1 per store. The subquery
groups by `oi2.product.productId`, not by `oi2.product`: EclipseLink expands an entity in `GROUP BY` to all of its
columns, and Oracle cannot group by the product's LOBs (`+ORA-22848+`). For the top N,
either run the `RANK()` SQL as a native query, or select per store ordered by units with `setMaxResults(N)`.

[[CO_SCHEMA_A_05]]
==== CO_SCHEMA_A_05: Rebalance stock between stores

With `0 <= :minStock <= :targetStock`, for each stocked product below `:minStock` at a store, propose the nearest store above `:targetStock` as the donor, the larger surplus and then the lower `store_id` at a tie, and a donor with no distance only as a fallback; propose no more than the need or the surplus.

[source,sql]
----
WITH short AS (SELECT store_id, product_id, :targetStock - product_inventory AS need
               FROM inventory
               WHERE product_inventory < :minStock),
     spare AS (SELECT store_id, product_id, product_inventory - :targetStock AS surplus
               FROM inventory
               WHERE product_inventory > :targetStock),
     pairs AS (SELECT sh.store_id AS to_store_id,
                      sp.store_id AS from_store_id,
                      sh.product_id,
                      sh.need,
                      sp.surplus,
                      6371 * ACOS(GREATEST(-1, LEAST(1,
                          SIN(t.latitude * ACOS(-1) / 180) * SIN(f.latitude * ACOS(-1) / 180)
                          + COS(t.latitude * ACOS(-1) / 180) * COS(f.latitude * ACOS(-1) / 180)
                            * COS((t.longitude - f.longitude) * ACOS(-1) / 180)))) AS km
               FROM short sh
                        JOIN spare sp ON sp.product_id = sh.product_id AND sp.store_id <> sh.store_id
                        JOIN stores t ON t.store_id = sh.store_id
                        JOIN stores f ON f.store_id = sp.store_id),
     ranked AS (SELECT p.*,
                       ROW_NUMBER() OVER (PARTITION BY to_store_id, product_id
                           ORDER BY km ASC NULLS LAST, surplus DESC, from_store_id) AS rn
                FROM pairs p)
SELECT t.store_name AS to_store, f.store_name AS from_store, r.product_id, ROUND(r.km) AS km,
       LEAST(r.need, r.surplus) AS transfer_qty
FROM ranked r
         JOIN stores t ON t.store_id = r.to_store_id
         JOIN stores f ON f.store_id = r.from_store_id
WHERE r.rn = 1
ORDER BY r.km NULLS LAST, t.store_name, r.product_id
----

The distance is the great-circle distance between the stores' coordinates, a stand-in for the cost of shipping. The
`Online` store has no coordinates, so its distance is null and it is proposed only when no physical store can help.
With `:minStock` 2 and `:targetStock` 10, 64 shortages can be covered from 136 candidate pairs; the nearest is
Vienna sending one unit of product 9 to Utrecht, 915 km away.

[source,jpaql]
----
SELECT need.store.storeName, spare.store.storeName, need.product.productId,
       :targetStock - need.productInventory, spare.productInventory - :targetStock
FROM Inventory need
         JOIN Inventory spare ON spare.product = need.product AND spare.store <> need.store
WHERE need.productInventory < :minStock
  AND spare.productInventory > :targetStock
ORDER BY need.store.storeName, need.product.productId
----

// JPQL NOT YET UPDATED: the SQL above changed.

JPQL has neither trigonometric functions nor window functions, so it stops at the candidate pairs — every shortage
with every store that could cover it. Compute the distances from `Store.latitude` / `Store.longitude` and keep the
nearest donor in Java.

Both solutions propose each shortage independently, so one donor can be promised to several shortages beyond its
surplus. To turn proposals into transfers, walk them nearest first, decrease each donor's remaining surplus as you go,
and apply each move — the donor's `productInventory` down, the receiver's up — in one transaction, so stock is never
counted twice or lost in between.

EclipseLink 5 accept but the specification does not promise. (EclipseLink 5.0 also fails to compile
`EXTRACT(... FROM LOCAL DATE)`, which is why the year is not derived inside the query.) The installed orders are from
2021 and 2022, so on the sample data the answer is empty; bind an earlier `:yearStart` to see rows.

[[CO_SCHEMA_A_12]]
==== CO_SCHEMA_A_12: Packing slips in one round trip

The warehouse prints a packing slip for each shipment: the lines it carries and each line's product. Loading the items
and then each product lazily costs one query per line; load them together.

[source,sql]
----
SELECT oi.order_id, oi.line_item_id, p.product_name, oi.quantity, sh.delivery_address
FROM shipments sh
         JOIN order_items oi ON oi.shipment_id = sh.shipment_id
         JOIN products p ON p.product_id = oi.product_id
WHERE sh.shipment_id = :shipmentId
ORDER BY oi.order_id, oi.line_item_id
----

[source,jpaql]
----
SELECT oi
FROM OrderItem oi
         JOIN FETCH oi.product
         JOIN FETCH oi.shipment
WHERE oi.shipment.shipmentId = :shipmentId
ORDER BY oi.id.orderId, oi.id.lineItemId
----

[source,jpaql]
----
SELECT o
FROM Order o
         JOIN FETCH o.customer
         JOIN FETCH o.store
WHERE o.orderId = :orderId
----

A fetch join takes no identification variable in the specification, so a chain such as shipment → items → product is
written from the many side, as above; going the other way needs an entity graph (`jakarta.persistence.fetchgraph`).

[[CO_SCHEMA_A_13]]
==== CO_SCHEMA_A_13: Store ranking and share of sales

The regional manager wants each store's revenue from completed orders, `0` for a store with none, its rank, its share of the chain's total, and a running total from the best store down; stores with the same revenue are ordered by `store_id`.

[source,sql]
----
WITH revenues AS (SELECT s.store_id, s.store_name, COALESCE(SUM(oi.unit_price * oi.quantity), 0) AS revenue
                  FROM stores s
                           LEFT JOIN orders o ON o.store_id = s.store_id AND o.order_status = 'COMPLETE'
                           LEFT JOIN order_items oi ON oi.order_id = o.order_id
                  GROUP BY s.store_id, s.store_name)
SELECT store_id,
       store_name,
       revenue,
       RANK() OVER (ORDER BY revenue DESC)                                          AS revenue_rank,
       ROUND(100 * revenue / NULLIF(SUM(revenue) OVER (), 0), 2)                   AS share_pct,
       SUM(revenue) OVER (ORDER BY revenue DESC, store_id ROWS UNBOUNDED PRECEDING) AS running_total
FROM revenues
ORDER BY revenue DESC, store_id
----

[source,jpaql]
----
SELECT s.storeName, SUM(oi.unitPrice * oi.quantity) AS revenue
FROM OrderItem oi
         JOIN oi.order o
         JOIN o.store s
GROUP BY s.storeId, s.storeName
ORDER BY revenue DESC
----

// JPQL NOT YET UPDATED: the SQL above changed.

There is no portable JPQL for `RANK()`, `+RATIO_TO_REPORT+` or a running `SUM() OVER`. Fetch the revenue per store,
already ordered, and compute rank, share and running total in Java; or run the SQL as a native query. The
`+STORE_ORDERS+` view (not an entity, see `StoreOrder`) adds the `GROUPING SETS` subtotals per status and the grand
total:

[source,sql]
----
SELECT total, store_name, order_status, order_count, total_sales
FROM store_orders
ORDER BY store_name NULLS LAST, order_status NULLS FIRST
----

[[CO_SCHEMA_A_14]]
==== CO_SCHEMA_A_14: Brands and reviews from the product JSON

Merchandising wants every product of a brand with its colour, and the products whose average review score is 8 or
better. The brand, colour and reviews live in the JSON document in `+PRODUCTS.PRODUCT_DETAILS+`.

[source,sql]
----
SELECT p.product_id, p.product_name,
       JSON_VALUE(p.product_details, '$.colour') AS colour
FROM products p
WHERE JSON_VALUE(p.product_details, '$.brand') = :brand
ORDER BY p.product_name
----

[source,sql]
----
SELECT product_name, ROUND(AVG(rating), 2) AS avg_rating, COUNT(*) AS reviews
FROM product_reviews
GROUP BY product_name
HAVING AVG(rating) >= 8
ORDER BY avg_rating DESC, product_name
----

No portable JPQL equivalent: `productDetails` is a `+byte[]+` LOB, and JPQL has no JSON operators. Either load the
products, bind each document to `ProductDetails` through `Product.getProductDetailsAsMapped(...)` with a JSON library,
and filter in Java; or run the SQL as a native query. `+FUNCTION('JSON_VALUE', ...)+` reaches the database function,
but its result type and its portability are the provider's business, not the specification's. `+PRODUCT_REVIEWS+` is mapped only as the plain class `ProductReview`, not as an entity.

[[CO_SCHEMA_A_15]]
==== CO_SCHEMA_A_15: Products often bought together

Merchandising is planning "bought together" suggestions for the web shop. List the ten pairs of products that appear
together in the most orders.

[source,sql]
----
SELECT pa.product_name, pb.product_name AS other_product_name, COUNT(*) AS orders
FROM order_items a
         JOIN order_items b ON b.order_id = a.order_id AND b.product_id > a.product_id
         JOIN products pa ON pa.product_id = a.product_id
         JOIN products pb ON pb.product_id = b.product_id
GROUP BY a.product_id, pa.product_name, b.product_id, pb.product_name
ORDER BY orders DESC, pa.product_name, pb.product_name
FETCH FIRST 10 ROWS ONLY
----

[source,jpaql]
----
SELECT pa.productName, pb.productName, COUNT(a) AS orders
FROM OrderItem a
         JOIN a.product pa,
     OrderItem b
         JOIN b.product pb
WHERE b.order = a.order
  AND pb.productId > pa.productId
GROUP BY pa.productId, pa.productName, pb.productId, pb.productName
ORDER BY orders DESC, pa.productName, pb.productName
----

A self-join of `+ORDER_ITEMS+` on the order pairs every line with every other line of the same order.
`+b.product_id > a.product_id+` keeps one of the two orderings of each pair and drops a line's pairing with itself.
`+(ORDER_ID, PRODUCT_ID)+` is unique, so a pair occurs at most once per order and `+COUNT(*)+` counts orders. Limit the
JPQL with `query.setMaxResults(10)`. The pair at the top, `Girl's Coat (Blue)` with `Girl's Trousers (Red)`, shares 9
orders; the tenth pair shares 6, and 31 other pairs share 6 too, so a different tie-break would give a different tenth
row.

[[CO_SCHEMA_A_16]]
==== CO_SCHEMA_A_16: Stock a store has never sold

A store manager wants to clear shelf space. List the products their store holds stock of but has never sold, the
largest stock first.

[source,sql]
----
SELECT p.product_name, i.product_inventory
FROM inventory i
         JOIN products p ON p.product_id = i.product_id
WHERE i.store_id = :storeId
  AND i.product_inventory > 0
  AND NOT EXISTS (SELECT 1
                  FROM order_items oi
                           JOIN orders o ON o.order_id = oi.order_id
                  WHERE o.store_id = i.store_id
                    AND oi.product_id = i.product_id)
ORDER BY i.product_inventory DESC, p.product_name
----

[source,jpaql]
----
SELECT e
FROM Inventory AS e
WHERE e.store = :store
  AND e.productInventory > 0
  AND NOT EXISTS (SELECT oi
                  FROM OrderItem oi
                  WHERE oi.product = e.product
                    AND oi.order.store = e.store)
ORDER BY e.productInventory DESC, e.product.productName ASC
----

In the JPQL, the anti-join is correlated on two columns at once: a sale only counts when it is of the same product _and_
was made at the same store. A product the store sold even once is not dead stock, however long ago that was. For store
20 (`Mexico City`) the answer is `Women's Jacket (Black)`, 7 units, and `Boy's Shirt (White)`, 2 units.

[[CO_SCHEMA_A_17]]
==== CO_SCHEMA_A_17: Month-over-month sales

Finance wants the revenue of completed orders per month, next to the month before and the change in per cent.
`LAG` takes the previous month that has sales, not the previous calendar month.

[source,sql]
----
SELECT order_month,
       revenue,
       LAG(revenue) OVER (ORDER BY order_month)                                       AS previous_revenue,
       ROUND(100 * (revenue - LAG(revenue) OVER (ORDER BY order_month)) / LAG(revenue) OVER (ORDER BY order_month), 1) AS change_pct
FROM (SELECT TRUNC(o.order_tms, 'MM') AS order_month, SUM(oi.unit_price * oi.quantity) AS revenue
      FROM orders o
               JOIN order_items oi ON oi.order_id = o.order_id
      WHERE o.order_status = 'COMPLETE'
      GROUP BY TRUNC(o.order_tms, 'MM'))
ORDER BY order_month
----


[[CO_SCHEMA_A_18]]
==== CO_SCHEMA_A_18: Shipments that carry nothing

Before dispatch, logistics wants the shipments that no order line is assigned to, with their store, customer and status.

[source,sql]
----
SELECT sh.shipment_id, sh.store_id, sh.customer_id, sh.shipment_status
FROM shipments sh
WHERE NOT EXISTS (SELECT 1 FROM order_items oi WHERE oi.shipment_id = sh.shipment_id)
ORDER BY sh.shipment_id
----
